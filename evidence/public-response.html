파일 본문과 붙여넣은 원문은 전송하지 않고 파일명·크기·텍스트 길이로 이벤트를 구성했습니다.

실패 처리

끊긴 연결을 다시 시도

최대 200건의 임시 큐와 5초 간격 재전송을 두고, 같은 사이트의 경고는 30초 간격으로 제한했습니다.

담당 범위와 구현 메모 보기

담당: 이벤트 수집, PC 식별 정보 추가, 중앙 API 전송, 로컬 경고. 팀 대시보드·중앙 서버·상관분석 엔진은 별도 담당 영역입니다.

정확한 의미: 파일 선택은 업로드 시도를 나타내며 업로드 완료나 정보 유출을 확정하지 않습니다. 실제 차단은 하지 않고, 붙여넣기는 전송만 합니다. 재전송 큐는 Agent 종료 시 사라집니다.

화면 기록: 원본 Streamlit 대시보드에 합성 테스트 이벤트 15건을 로컬 API로 공급하고, 기존 위험도 규칙과 분석 엔진으로 처리했습니다. 테스트 단말 9대 중 우선 검토 2대·관찰 2대·정상 5대로 집계되었고, 선택한 사례는 85점입니다. 실제 운영 활동이나 사고 건수를 뜻하지 않습니다. 테스트 실행임을 알리는 문구를 추가했으며, 점수 계산과 대시보드 구성은 원본을 사용했습니다. 팀 대시보드는 프로젝트 전체를 보여주는 화면이며, 제 담당은 Agent·Chrome 확장·로컬 경고 영역입니다.

역할 분리

탐지는 규칙, 요약은 AI 보조

탐지와 위험도는 명시적 조건으로 계산합니다. 선택적으로 연결하는 LLM은 구조화된 결과의 자연어 요약을 맡습니다.

오류 해결과 검증 기록 보기

화면과 분석 분리: 긴 로그의 그래프가 늘어지는 문제는 원본 탐지 입력을 유지하고 시각화용 데이터만 필터링해 정리했습니다.

2026.09.14 재실행: 저장소의 sample_attack_logs.csv를 웹 화면에 업로드해 유효 로그 8건·로그인 실패 7건·탐지 이벤트 3건, 종합 위험도 55/100을 확인했습니다. 해당 샘플의 결과이며 탐지 정확도 지표는 아닙니다.

PROJECT 03 / PERSONAL실제 Nginx 로그 지속 감시 · 대시보드

Mini SOC

탐지 다음의 과정까지
하나의 흐름으로.

로그를 읽고 경보를 만든 뒤 위험도 판단·승인·대응 시뮬레이션·사건 저장·대시보드·보고서까지 이어지는 미니 보안관제 프로젝트입니다. 샘플 로그뿐 아니라 Docker Nginx의 access.log에 새로 추가되는 요청을 지속 감시하도록 확장했습니다.

  • Python
  • Flask REST API
  • Docker · Nginx
  • JSON
  • Markdown
소스·데모 실행 방법 ↗
2026.09.15 실행 확인샘플 로그 11건 → 경보 6건
실제 Nginx 404 요청 → http_error 자동 탐지 → 대시보드 반영
  1. 01
    실제 로그 지속 감시

    Docker Nginx access.log의 새 줄을 증분으로 읽어 이벤트화

  2. 02
    시간창 기반 이상행위 탐지

    HTTP Error · Brute Force · Password Spraying · Night Login

  3. 03
    위험도 판단 · HIGH 승인

    LLM 미설정·실패 시 규칙 기반 fallback, 고위험 대응 전 승인

  4. 04
    사건 기록 · 대시보드 · 보고서

    incidents.json, Flask 대시보드, Markdown 일일 보고서로 결과 보존

오탐 보완

시간창 없는 탐지를 줄이다

Password Spraying을 단순 다계정 누적이 아니라 300초 안에 서로 다른 계정 3개 이상 실패한 경우로 제한했습니다. Brute Force는 초 단위 시각도 처리하도록 보완했습니다.

실시간성

한 번 읽고 끝나는 데모에서 지속 감시로

기존 sample_server.log 1회 분석 외에 live_monitor.py를 추가해 실행 이후 새로 생기는 로그만 읽고, 동일 경보는 5분 쿨다운으로 반복 알림을 줄였습니다.

실행 범위와 AI 활용 방식 보기

샘플 데모: sample_server.log의 이벤트 11건에서 HTTP Error, Brute Force, Password Spraying, Night Login 규칙으로 6개 경보가 생성되도록 구성했습니다. HIGH 경보는 승인 후 block_ip 대응을 시뮬레이션합니다.

실제 로그 확인: Docker Nginx를 8081 포트로 실행하고 run_live.py logs/access.log로 지속 감시했습니다. 존재하지 않는 경로 요청으로 404 로그를 만든 뒤 http_error → watch → POST /alert 201 → 대시보드 반영 순서를 확인했습니다.

범위: 계정 잠금과 IP 차단은 실제 시스템 변경이 아닌 시뮬레이션입니다. LLM API가 없거나 실패하면 규칙 기반 fallback을 사용하며, Slack Webhook이 없으면 알림 단계만 건너뜁니다.
